# 方案：质量优先（放弃省魔粒）与「NVIDIA 劣化不自动切换」的处置

> 2026-11-12 20:45。**只出方案，未改任何代码 / 配置 / 数据库**。
> 替代 `docs/plan-model-quality-floor.md`（该版以「省魔粒」为前提，已被本方案推翻）。
> 只写通用结构与实测口径，不含本机地址、凭据、个人信息。

## 1. 结论先行

1. **用户的观察成立**：ModelScope（渠道 `#35`）今日成功调用 **2 次**，NVIDIA（`#33`）**3273 次**，占比 0.06%。魔粒几乎零消耗不是额度问题，是流量根本没被路由过去。
2. **降级链没有坏，但只在「上游报错」时触发**：今日唯一一次生效是 20:10:46 `#33` 返回 500 → 20:10:48 / 20:10:49 两次落到 `#35` 并成功。`#33` 绝大多数劣化形态是**慢但最终返回 200**，网关判定成功，不重试、不降级；引擎 120 秒超时断开后网关仍跑完并记为 200（日志出现 `use_time_seconds` 361 / 362 / 367 / 478 秒，且无对应 channel error）。
3. **更该优先修的是质量塌陷**：`#33` 的 `free-auto` 当前映射到 `nvidia/nemotron-3.5-bolt-e4b`（4B 激活），导致全站评分系统性偏低 —— 均分 42.2（11-09）→ **27.7**（11-12），≥40 占比 41% → **16.4%**，Yahoo 达标率 23% → **3%**，板块页 `browseFloor=40` 之上几乎不刷新。这与「新闻几个小时没更新」的体感直接对应。
4. **质量优先的物理边界**：ModelScope 每日约 **250 魔粒、24 小时过期**，主流档 1 魔粒/次 ⇒ **250 次/日**；全站约 **3500 次/日**（近 24h 回执）。即使完全不省魔粒，ModelScope 也**最多覆盖 7%，永远不能当主力**。因此主力必须是免费池里的 ≥9B 模型。
5. **推荐结构**：NVIDIA `nemotron-3.5-super-vl-120b-a12b`（120B / 12B 激活，免费）作主力，ModelScope `Qwen/Qwen3.8-27B`（27B，1 魔粒/次）作高质量兜底，并发 2 → 4。**「按耗时自动切换」在不引入中间层、不改核心代码的前提下做不到**，改为「从源头消除慢 + 真报错时降级有意义 + 人工应急预案」。

### 2.4 一个被排除的嫌疑

`.env` 的 `LLM_REASONING_TOKENS=10000` 使生产请求 `maxTokens` 达到 11200–11500（`llm.ts:149`，回执样本实测 11200）。实测同一 prompt 下 `max_tokens=2700` 与 `11500` 耗时无差异（0.8–3.5s），**不是慢请求的原因**。但 120B 不产生 `reasoning_content` 且 `LLM_EXTRA_JSON` 已关思考链，这 10000 属无谓余量，建议一并清掉。

## 3. 为什么「劣化时不自动切换」修不了（机制边界）

- new-api 选渠按 `model` 字段硬过滤，再按 `priority` 从高到低**串行降级**；重试条件是**上游返回错误**，不是耗时。
- 引擎 `TIMEOUT_MS=120_000`（`llm.ts:161`）超时后主动断开，但网关侧上游请求仍在跑，最终返回 200 并记 consume log；客户端断开**不会**回写为渠道失败。
- 于是「慢但 200」的请求：网关算成功 → 不降级 → 不自动禁用 → 站点侧只看到 TimeoutError 与 `unknown` 回执。
- 站点侧 `fallbackFor` 路线也不可用：`FAILOVER_TIMEOUT_MS=30_000`，而 120B 长输出常 40s+，启用会打出大量双份请求；且该路径在本站从未被验证过。
- ⇒ **除非在网关前加一层超时代理，或改网关代码/核心 `llm.ts`，否则做不到按耗时自动切换**。两者都超出「只动配置、不动 `packages/`」的约定，本方案不采纳。

**替代思路**：把 `#33` 的映射换成实测 4–14 秒的 120B，让「慢」不再发生；把 `#35` 换成 27B，让真报错时的降级有质量意义；再把人工切换写进运维预案。

## 4. 目标配置（5 处，全配置层，不动 `packages/` / `apps/`）

| # | 位置 | 现值 | 目标 | 理由 |
|---|---|---|---|---|
| 1 | 网关 `#33` `model_mapping.free-auto` | `nvidia/nemotron-3.5-bolt-e4b` | **`nvidia/nemotron-3.5-super-vl-120b-a12b`** | 120B / 12B 激活，≥9B，免费；实测并发 4 可用、JSON 正常 |
| 2 | 网关 `#35` `model_mapping.free-auto` | `nex-agi/Nex-N2.5-mini`（轻量 0.5） | **`Qwen/Qwen3.8-27B`**（主流 1 魔粒） | 放弃省魔粒；27B 与主力质量对齐，短 JSON 快 |
| 3 | `.env` | `LLM_MAX_CONCURRENCY=2` | **4** | 已拍板；实测 120B 支持 4 并发 |
| 4 | `.env` | `LLM_REASONING_TOKENS=10000` | **0** | 无思考链，去掉无谓的 11200 token 上限 |
| 5 | `.env` | `LLM_MODEL=free-auto` | **保持不变** | 保留别名才能走两级路由；钉死具体模型名会失去兜底 |

`#35` priority 保持 **185（低于 `#33`）**：ModelScope 每日仅 250 次，若提到主位会在约 1 小时内耗尽，之后全站只剩 NVIDIA，风险反而更大。
不重新启用 dashscope / ds-*（按用户决定），#23–#26、#36 等维持 `status=2`。

## 5. 关于「让魔粒真正被用起来」

每日 250 魔粒 24 小时过期，不用即作废。但「等降级」的被动方式今天只触发 2 次，等于白留。两条主动分流路径经评估后**均不推荐本期做**：

| 路径 | 做法 | 评估 |
|---|---|---|
| A. 网关权重分流 | `#33`/`#35` 设同 priority、weight 13:1，约 250 次/日走 27B | 简单、零代码，但**同一批条目会由不同模型评分**，可能重新引入评分分布分裂，与「修系统性低分」目标冲突 |
| B. 按步骤分级（`site/models.ts`） | 新增复用 `LLM_BASE_URL` / `LLM_API_KEY` 的 preset，把小量高价值步骤钉到 27B | 250 次/日只够覆盖 `groupReview`(91) + `understand`(69) ≈ 160 次，而这些恰是长输出步骤；实测 27B 长输出 1/2 超时 ⇒ **反而降质** |

**推荐：不主动分流。**「放弃省魔粒」的含义是不为省钱牺牲质量，不等于必须把额度花光。27B 的定位是「真报错时的高质量兜底」+「NVIDIA 劣化时的人工应急通道」，每日额度闲置是可接受成本。

## 6. 实施、验证与回滚

### P0｜一次性维护窗口（网关 + api/worker 合并重启，避免两次打断）

1. 备份：网关整库 + `channels` 表 JSON（含模型映射/优先级）、`.env`。
2. 停 `new-api` → 改 #33 / #35 的 `model_mapping` → checkpoint → 回传 → 清理 WAL/SHM → 启动。
3. 改 `.env` 三行（并发 4、reasoning 0），`docker compose up -d --force-recreate --no-deps api worker`。
4. 用官方 `releaseReceipt` 路径放行 3h 窗口内的 `unknown` 回执（当前全表 102 条，多数为 11-11 故障遗留、已超窗，**只放行窗口内的**）。
5. 冒烟：`free-auto` 最小请求返回合法 JSON；`unsupportedConfig` 不涉及（未改 sources）。

### P1｜观察 2 小时后判定

| 指标 | 期望 |
|---|---|
| 全站均分 / ≥40 占比 | 从 27.7 / 16.4% 回升，向 40+ / 30%+ 靠拢 |
| `content=null` / `unusable output` | 0（若出现，先查 `finish_reason=length`） |
| 120s 超时、`unknown` 回执 | 不高于现状 |
| 各板块最后卡片时间 | 30 分钟内有新增 |
| 网关渠道分布 | `#33` 主力、`#35` 仅在报错时少量出现 |
| 吞吐 | 并发 4 下不低于当前约 8–10 次/分钟 |

若 120B 出现持续卡死（复现「2/4 卡 150s」），**降回并发 2** 优先于换回 4B；4B 不再作为回退选项（质量下限）。

### P2｜长期

- 给「达标率骤降 / 超时率 / unknown 积压」加告警，避免再次靠人工发现「没更新」。
- 若日后需要真正的按耗时降级，单独评估网关前超时代理或网关侧渠道超时能力。

### 回滚

- `.env`：从备份恢复三行，recreate api/worker。
- 网关：从备份库恢复 `channels.model_mapping` 两行（或整库回传），重启 `new-api`。
- 两条回滚都不需要 `rebuild`；恢复后按同一冒烟项验证。

## 7. 已知风险

1. **单点依赖**：启用渠道仍只有 `#33` / `#35` 两条，且 `#35` 每日仅 250 次。用户已明确不启用第三渠道，此为已接受风险。
2. **120B 偶发长请求卡死**：两轮并发 4 长输出测试一轮 2/4 卡死、一轮全通过。生产混合 prompt 下可能复现，届时先降并发、再考虑换 `nemotron-3.5-super-vl` 系列其他规格。
3. **重启代价**：网关重启与 worker 重建会打断在途请求，历史上每次产生数十条 `connect failed` 与少量 `unknown`；合并成一个窗口 + 事后放行可收敛。
4. **质量一致性**：换模型后历史评分与新评分不在同一分布，板块页会同时存在两个时期的卡片；不改评分标准，观察期不回刷历史。
