# 平台工作流配额受限时的备用方案

> 定位：本站是**自用 / 免费完全版**，不对外变现。本文只讨论「宿主平台侧自动化 / 定时任务条数被限制」时，如何保证站点照常启动、采集、出刊。
> 本文档会随仓库上传，因此**只写通用结构与命令**，不记录本机自动化清单、本机绝对路径、账号或凭证。具体盘点留在本机笔记里。
> 配套：`docs/sop.md`（日常命令）、`docs/deferred-items.md`（顺延事项）、`docs/plan-ai-finance.md`（方案与历史）。

---

## 1. 结论先行

**限制「工作流数量」不会打断本站主链路。** 本站的调度、采集、分析、出刊全部在 Docker 容器内完成（worker 内有十余条 pg-boss 定时任务），属于站点自身能力，不占用宿主平台的自动化名额：

| 环节 | 由谁调度 | 是否占用平台工作流名额 |
|---|---|---|
| 站点启动 / 自检 / 巡检 | `./up`（本地命令） | 否 |
| 信源采集 | worker 容器内 `sources.schedule`（pg-boss cron） | 否 |
| 内容分析、翻译、聚合 | worker 容器内 `content.*` 定时任务 | 否 |
| **日报 / 周报 / 月报出刊** | worker 容器内 `reports.compose`（`0,30 * * * *`，按 `site/site.ts` 的 `EDITION_TIMES` 判期，日报 09:30） | 否 |
| 保留期清理、告警、恢复、健康检查 | worker 容器内 `ops.*` 定时任务 | 否 |
| 外部要闻整理成 CSV → 反哺入站 | 宿主平台自动化（**可选增强**） | **是，但可省略** |
| 成文撰写 / 配图 / 站外推送 | 宿主平台自动化（站外能力） | 是，且不属于本站职责 |

两条硬事实支撑这个判断：

1. 站点自带 **23 个 RSS 源全部启用**，即使一条外部要闻都不反哺，也能自采出内容；`external` 源只是补充。
2. 大模型调用由 worker 读站内配置完成，不依赖宿主平台的内置模型。

所以备用方案的设计目标不是「把 24 条自动化搬个家」，而是**把链路里唯一可能受影响的第 1 层（调度）做成可替换件**，第 2、3 层一行不动。

---

## 2. 链路分层

```
第 1 层  调度触发     平台自动化 / 本机 launchd / 人工 ./up      ← 唯一可替换层
              ↓
第 2 层  内容入站     免费源 → CSV 留痕 → ./up ingest           ← 平台无关，已有
              ↓
第 3 层  处理与出刊   worker cron + 站内 LLM + DB + 3 个公开页   ← 站内自足，已有
```

**关键约定**：任何新增的外部供稿都必须经由 `./up ingest`（地址由 `.env` 的 `SITE_URL` 派生），不要在自动化里写死 URL 或端口。这样第 1 层无论换成谁，第 2、3 层都不用改。

---

## 3. 「限制」可能的三种形态与影响

| 形态 | 典型表现 | 对本站影响 | 应对 |
|---|---|---|---|
| **L1 条数上限** | 只允许 N 条（如 5 / 3 / 1） | 无直接影响；只影响站外撰写 / 推送任务 | 瘦身 + 合并同类 |
| **L2 并发 / 频率上限** | 同一时段只能跑 M 条，或每日总次数封顶 | 无直接影响；站内 cron 在容器内，不计入平台配额 | 错峰；把周期性任务下沉到站内 cron |
| **L3 完全停用** | 平台不再提供定时自动化 | 站点仍可启动、采集、出刊；仅失去站外写作 / 推送 | 切到本机 launchd；或维持「零自动化」运行 |

补充：若限制指的是 **CI 工作流文件数量**，本站只有 1 个 workflow，且只在 push / PR / 手动触发，没有 `schedule:`，本身不占定时配额；CI 只做校验，不参与内容生产。

## 4. 方案对比

| 方案 | 做法 | 覆盖到哪一步 | 成本 | 判断 |
|---|---|---|---|---|
| **A 零改动（现状即兜底）** | 什么也不做：靠 23 个 RSS 自采 + 站内 cron 出刊；`./up` 人工兜底 | 站点运行 + 出刊 **100%** | 0 | **立即生效，默认方案** |
| **B 名额瘦身 / 合并** | 暂停或删除过期、一次性、重复任务；同一时间窗的多条合并成 1 条总控 | 保住站外写作 / 推送 | 低（只改任务配置） | L1 时做 |
| **C 本机调度（终极兜底）** | 一条 launchd plist → 调 `./up` 系列命令；CSV 留痕落本机目录；不经过平台 | 脱离平台仍能跑完整链路 | 中（1 个 plist + 可选 1 个采集脚本） | L3 时做，**推荐提前写好** |
| **D CI 定时任务** | 给 workflow 加 `schedule:` | 只能做校验 / 构建 | 低但无效 | **不采用** |

**D 为什么不行**：CI runner 在公网、站点只监听本机 loopback，定时任务无法把结果反哺进本机接口；且公开仓库里放定时抓取逻辑会引入不必要的外部依赖与信息暴露。CI 的职责保持为「校验」即可。

## 5. 推荐路径：R0 → R3 阶梯

| 阶段 | 触发条件 | 动作 | 验收 |
|---|---|---|---|
| **R0** | 现在，无限制 | 确认「平台自动化 = 可选增强」并写入文档；保留 `./up check` / `./up smoke` 作为人工兜底 | `./up check` 全绿、`./up smoke` 全过、`/api/health` 返回 `{"ok":true,"db":"ok"}` |
| **R1** | 限制到 ≤5 条 | 清理过期一次性任务与长期暂停任务；同一时间窗的多条合并为 1 条 | 活跃任务数 ≤ 上限；站点数据条数不下降 |
| **R2** | 限制到 1–2 条 | 只留 1 条「总控」，负责需要模型判断 / 写作的站外任务；所有周期性动作下沉到站内 cron | 总控执行后 CSV 仍生成，`./up ingest` 仍能入站 |
| **R3** | 平台 0 条 | 切到本机 launchd + 仓库脚本；站外写作 / 推送改为手动导出或本机脚本 | 连续 2 天 09:30 日报自动落库，无需任何平台任务 |

**瘦身优先级（通用原则，不针对具体任务）**：
1. 先删已过期的一次性任务与长期暂停的重复任务 —— 它们不产出，只是占位；
2. 再合并同一时间窗内的同类任务（一个 prompt 内串多步）；
3. 最后才考虑把周期任务迁到站内 cron。**不要为了省名额而动站内 cron** —— 它们本来就不占平台配额。

## 6. R3 最小闭环：本机调度

### 6.1 现在就能用的等价命令（无需新增代码）

```bash
./up                 # 已在跑且健康时直接跳过构建，幂等，适合每天定时调用
./up check           # 只读确认环境
./up smoke           # 巡检页面、接口、RSS、MCP
./up ingest <file>   # 有外部 CSV 时入站；没有就完全跳过
./up ports           # 端口台账，排查多容器共存
```

站点只要容器在跑，09:30 日报由 worker 自动出刊，**不需要任何平台任务**。因此 R3 的最小闭环可以只有一条：每天固定时刻执行 `./up`（幂等、失败可重跑），其余交给站内 cron。

### 6.2 launchd 模板（占位符，实施时由安装脚本替换）

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>Label</key><string>local.dailyhot.daily</string>
  <key>ProgramArguments</key>
  <array>
    <string>/bin/zsh</string>
    <string><REPO_DIR>/up</string>
  </array>
  <key>WorkingDirectory</key><string><REPO_DIR></string>
  <key>StartCalendarInterval</key>
  <array>
    <dict><key>Hour</key><integer>9</integer><key>Minute</key><integer>20</integer></dict>
  </array>
  <key>RunAtLoad</key><false/>
  <key>ThrottleInterval</key><integer>300</integer>
  <key>StandardOutPath</key><string><LOG_DIR>/dailyhot-daily.log</string>
  <key>StandardErrorPath</key><string><LOG_DIR>/dailyhot-daily.err</string>
</dict>
</plist>
```

实施要点（写在这里，避免踩坑）：

- `<REPO_DIR>` / `<LOG_DIR>` 必须由安装脚本替换成真实绝对路径后再装到 `~/Library/LaunchAgents/`；**路径写错 launchd 会静默不跑，不报错，最难查**。
- 时间取 **09:20**：早于 09:30 出刊，给 `./up` 留启动窗口；`./up` 幂等，站点已跑时几秒结束。
- 关机错过的任务由 launchd 在下次开机补跑一次；`RunAtLoad=false` 避免每次登录多跑一遍。
- `ThrottleInterval=300` 防失败后疯狂重启。
- plist 属于**本机配置，不入库**；仓库里只保留这份模板与说明。
- 需要外部要闻时，把 `ProgramArguments` 换成 `<REPO_DIR>/scripts/…` 的采集脚本 + `./up ingest` 两步；采集脚本尚未实现（见第 8 节）。

### 6.3 验收清单

```bash
./up check                       # 全绿
./up smoke                       # all checks passed
./up status                      # 4 容器 Up + health {"ok":true,"db":"ok"}
./up ports                       # 无端口冲突
# 次日核对日报是否落库（kind|key 形如 daily|YYYY-MM-DD）
```

数据条数与日报 key 在切换前后应保持一致；切换只改调度层，**不应触碰数据卷**（禁止 `down -v`）。

## 7. 站外能力怎么处理

平台自动化里真正会受名额影响的，是「成文撰写 / 配图 / 推送到站外渠道」。按本站「自用 / 免费完全版」的定位，处理原则：

- **优先保站内**：站点运行、采集、出刊、页面与机器出口（RSS / MCP / API）是主链路，任何情况下先保这些。
- **站外写作降级为手动**：需要成文时，从站内 `/daily`、RSS 或后台导出，再人工处理；不为此新增平台任务。
- **CSV 留痕不丢**：外部要闻的留痕是文件，落在本机目录即可；`./up ingest` 接受 CSV / JSON / stdin，不挑来源。
- **推送渠道另议**：站内已有 `ops.digest` 与告警定时任务；是否启用取决于配置，与平台工作流名额无关。

## 9. 一句话备忘

**调度可以换，数据不用迁，端口不用改，代码不用动。** 真被限到只剩 1 条甚至 0 条时，执行 `./up` 即可；09:30 的日报由 worker 自己出。
